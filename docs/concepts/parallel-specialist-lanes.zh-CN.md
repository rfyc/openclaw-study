并行专业通道让一个网关将不同的聊天或房间路由到不同的智能体，同时保持用户体验的速度。诀窍是将并行性视为稀缺资源设计问题，而不仅仅是"更多智能体"。

## 基本原则

专业通道只有在减少真正瓶颈的竞争时才能提高吞吐量：

- **会话锁**：一次只有一个运行应该改变给定的会话。
- **全局模型容量**：所有可见的聊天运行仍然共享提供商限制。
- **工具容量**：shell、浏览器、网络和仓库工作可能比模型轮次本身更慢。
- **上下文预算**：长记录使每个未来轮次更慢，聚焦度更低。
- **所有权歧义**：做同样工作的重复智能体浪费容量。

OpenClaw 已经通过[命令队列](/concepts/queue)按会话序列化运行并限制全局并行性。专业通道在顶部添加策略：哪个智能体拥有哪项工作，什么留在聊天中，什么变成后台工作。

## 推荐推出

### 阶段 1：通道合约 + 后台重型工作

在其工作区和系统提示中给每个通道一份书面合约：

- **目的**：此通道拥有的工作。
- **非目标**：它应该交接而不是尝试的工作。
- **聊天预算**：快速回答保留在聊天中；长任务应该简短确认，然后在后台子智能体或任务中运行。
- **交接规则**：当另一个通道拥有该工作时，说明它应该去哪里并提供紧凑的交接摘要。
- **工具风险规则**：优先选择能完成工作的最小工具界面。

这是最便宜的阶段，解决了大多数堵塞问题：一个编码任务不再使研究通道变得迟缓，每个聊天保持自己的上下文干净。

### 阶段 2：优先级和并发控制

根据每个通道的业务价值调整队列和模型容量：

```json5
{
  agents: {
    defaults: {
      maxConcurrent: 4,
      subagents: { maxConcurrent: 8 },
    },
  },
  messages: {
    queue: {
      mode: "collect",
      debounceMs: 1000,
      cap: 20,
      drop: "summarize",
    },
  },
}
```

对高优先级工作使用直接/个人聊天和生产运营智能体。当系统忙碌时，让研究、起草和批量编码转到后台任务。

### 阶段 3：协调者/流量控制器

一旦多个通道处于活跃状态，添加一个小型协调者模式：

- 追踪活跃通道任务和所有者。
- 检测跨群组的重复请求。
- 在通道之间路由交接摘要。
- 只呈现阻碍因素、已完成的结果和人类必须做出的决定。

不要从这里开始。没有通道合约的协调者只是协调混乱。

## 最小通道合约模板

```md
# 通道合约

## 拥有

- <此通道负责的工作>

## 不拥有

- <要交接的工作>

## 聊天预算

- 直接回答快速问题。
- 对于多步骤、慢速或工具密集的工作：简短确认，派生/后台处理，然后在完成时返回结果。

## 交接

如果另一个通道拥有该请求，回复包含：

- 目标通道
- 目标
- 相关上下文
- 确切的下一步行动

## 工具姿态

使用能完成任务的最小工具界面。除非此通道明确拥有它，否则避免广泛的 shell 或网络工作。
```
