# 事件响应

## 1. 检测和分类

我们监控以下来源的安全信号：

- GitHub 安全公告（GHSA）和私人漏洞报告。
- 当报告不敏感时，公开的 GitHub issues/讨论。
- 自动化信号（例如 Dependabot、CodeQL、npm 公告和秘密扫描）。

初始分类：

1. 确认受影响的组件、版本和信任边界影响。
2. 使用仓库 `SECURITY.md` 范围和范围外规则，将其分类为安全问题或加固/无需操作。
3. 事件负责人相应地响应。

## 2. 评估

严重性指南：

- **严重：** 包、发布或仓库被攻陷、主动利用，或具有高影响控制或数据暴露的未经认证信任边界绕过。
- **高：** 经验证的信任边界绕过，需要有限前提条件（例如已认证但未授权的高影响操作），或 OpenClaw 拥有的敏感凭据暴露。
- **中：** 具有实际影响但可利用性受限或有大量前提条件的重大安全弱点。
- **低：** 深度防御发现、范围狭窄的拒绝服务，或没有已证明信任边界绕过的加固/同等差距。

## 3. 响应

1. 向报告者确认收到（敏感时私下进行）。
2. 在受支持的版本和最新的 `main` 上复现，然后通过回归覆盖实现并验证补丁。
3. 对于严重/高级事件，尽可能快速地准备修补版本。
4. 对于中/低级事件，在正常发布流程中打补丁并记录缓解指南。

## 4. 沟通

我们通过以下渠道进行沟通：

- 受影响仓库中的 GitHub 安全公告。
- 已修复版本的发布说明/变更日志条目。
- 直接向报告者跟进状态和解决情况。

披露政策：

- 严重/高级事件应接受协调披露，在适当时发布 CVE。
- 低风险加固发现可以记录在发布说明或公告中，根据影响和用户暴露情况决定是否发布 CVE。

## 5. 恢复和跟进

在发布修复后：

1. 在 CI 和发布制品中验证修复措施。
2. 进行简短的事后审查（时间线、根本原因、检测差距、预防计划）。
3. 添加后续加固/测试/文档任务并跟踪至完成。
