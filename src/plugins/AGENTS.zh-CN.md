## 边界规则

- 保持控制平面和运行时平面关注点分离：
  发现、清单解析、配置验证、设置/入职提示和激活规划属于控制平面；实际插件执行属于运行时解析。
- 保持清单优先的行为：发现、配置验证和设置应在插件运行时执行之前从元数据中工作。
- 缓存概念：除非调用者拥有当前流程的显式 `PluginMetadataSnapshot`、`PluginLookUpTable` 或清单注册表，否则元数据保持新鲜。不要为发现、清单注册表、已安装索引重建、所有者查找、模型抑制、提供商策略、公共产物元数据或类似控制平面答案添加持久化元数据缓存。一旦代码或已安装产物实际加载，运行时加载器、jiti/模块和依赖产物缓存是允许的缓存层。
- 保持加载器行为与文档化的 Plugin SDK 和清单契约对齐。不要创建捆绑插件可以使用但外部插件无法使用的私有后门。
- 在发现和激活流程中保持惰性。加载器、注册表和公共产物变更不得在元数据、轻量级导出或类型化契约足够的情况下急切地导入捆绑插件运行时桶文件。
- 如果插件暴露独立的轻量级和重量级运行时层面，在实际执行需要重量级模块之前，将发现、库存和设置状态检查保持在轻量级路径上。
- 如果加载器或注册表变更影响插件作者，更新公共 SDK、文档和契约测试，而非依赖偶然的内部实现。
- 优先使用从清单/描述符所有权出发的显式激活规划，而非"加载此范围内的所有内容"行为。广泛的注册表实例化应是例外，而非设计核心。
- 不要通过在不相关的核心路径中散布对 `plugins.entries.<id>.config` 的直接读取来将"插件拥有"规范化为"核心拥有"。优先使用通用辅助工具、插件运行时钩子、清单元数据和显式自动启用连接。
- 当插件拥有的工具或提供商回退需要核心参与时，保持契约的通用性，并遵守插件禁用加上 SecretRef 语义。
- 保持契约加载和契约测试在专用的捆绑注册表路径上。不要使契约验证依赖于通过不相关的生产解析流程激活提供商。
- 优先使用共享提供商系列辅助工具，而非插件注册表钩子中的临时策略。如果多个提供商需要相同的重放策略、工具兼容性、流包装组合或负载修补行为，在添加另一个插件本地 lambda 之前集中化该辅助工具。
- 保持提供商策略层分离：
  认证/目录/入职保持插件拥有，
  传输/重放/工具兼容性系列属于共享辅助工具，
  注册表/运行时代码应组合这些层，而非内联重新编码策略。
- 当提供商钩子增长嵌套的包装组合链或重复的兼容性标志时，将其视为退化信号。提取共享辅助工具或组合器，而非让一个插件继续携带近似副本。
- 将可变的全局运行时注册表状态视为兼容性脚手架，而非请求时执行的期望真实来源。在添加新的运行时流程时，优先使用不可变或请求范围的句柄。
- 如果设置、发现或 doctor 流程需要插件运行时，明确并窄化该需求。不要让冷控制平面路径悄悄地导入宽泛的运行时层面。
- 解析器和公共层面加载器测试必须对宽泛的 `api.js` / `runtime-api.js` 回退行为使用生成的微型插件固件。不要仅为证明路径解析而将那些测试指向真实捆绑插件源 API。

## 验证

- 如果修改可能改变捆绑插件导入扇出的加载器、注册表、激活或公共产物代码，运行 `pnpm build`。
- 如果变更可能改变捆绑插件的启动成本，使用以下命令重新分析受影响的插件入口点：
  `OPENCLAW_LOCAL_CHECK=0 node scripts/profile-extension-memory.mjs --extension <id> --skip-combined --concurrency 1`
